# Blocker V2 Stage 2 — advanced static cosmetics

Phase 2D.2 adds a bounded standards-based CSS subset to Paper's existing host-scoped cosmetic rules. Paper still supplies the sole declaration, `display:none!important`; list text cannot inject arbitrary CSS or JavaScript. The parser accepts validated attribute selectors, child/descendant/sibling combinators, a single constrained `:has()`, and a short allowlist of other CSS pseudo-classes. It rejects complex/nested procedures, broad selectors, declarations, unsupported syntax, and selectors over length/complexity limits. WebKit's `CSS.supports` also checks advanced selectors at runtime before insertion.

Admission considers up to 24,000 cosmetic candidates per source and retains at most 4,000. The ranking reserves limited capacity for domain-scoped ad custom elements and advanced domain rules, then fills with ordinary static rules. Exact global and domain-scoped cosmetic exceptions are resolved before injection. Only rules relevant to the current host are selected, capped at **500 selectors and 32 KiB** per page. Site scripts are cached for at most **24** source-version/host/settings keys.

The generated `WKUserScript` runs at document start in the main frame. Its style sheet applies to matching elements added later by SPA navigation, so a continuous `MutationObserver`, polling loop, or procedural evaluator was not justified by the local fixture results. The script counts distinct initial matches at DOMContentLoaded for honest diagnostics; that count is not a lifetime count or a request-block count. Domain changes across full navigation rebuild the host-specific script. Script-only route changes to a different relevant host are not possible, while same-host route-specific list scopes are not modeled. Cross-origin subframes are outside this main-frame CSS scope.

Local WebKit tests exercised `:has()`, attribute selectors including an escaped promoted marker, a Reddit-style custom ad element, host scoping, global/domain exceptions, SPA-added cards, and survival of navigation, login, form, purchase, video, and consent controls in the fixture. The local fixture establishes selector behavior, not live-site ad-removal rates. No page-world scriptlets, response manipulation, YouTube player changes, or procedural DOM engine ship in this stage. Video ads remain a known limitation.

Performance details and raw measurements are in [blocker-performance.md](blocker-performance.md). Live public-site and hands-on visual verification remain limited as recorded in [known limitations](known-limitations.md).
