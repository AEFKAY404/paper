# Known limitations — Phase 2B

- URL restoration reopens tabs and preserves their order and active index. It does not restore form state, per-tab back/forward history, scroll position, or in-memory JavaScript state after app relaunch.
- Isolated-bundle XCTest UI scenarios now verify several native keyboard paths and new-tab focus. Webpage keyboard/mouse interaction and trackpad scrolling still need hands-on verification.
- WebKit history swipes are enabled by default, and the preference now updates open sessions. Option-swipe tab switching remains opt-in and needs physical trackpad verification. App-local swipe events cannot prove behavior over every nested scroller, webpage drag target, Mission Control configuration, or fullscreen desktop gesture; use Control-Tab and Control-Shift-Tab if it conflicts.
- Tab overview previews are static and may be stale until navigation completes or their five-minute freshness limit expires; viewport-only and script-only page changes do not invalidate them immediately. A never-visible, loading, failed, or unsnapshotable page shows a placeholder. Preview capture is bounded; it is not a live miniature web view.
- `⌘⇧\` and overview search/dismissal passed synthetic UI automation. Physical keyboard and VoiceOver focus order still need hands-on checks.
- Save Panel downloads are implemented but an end-to-end saved-file check remains. File-overwrite behavior and server-provided filenames need manual confirmation.
- Popup requests with a URL open in a new tab. A script-created blank popup with no URL is not represented yet.
- Browser state is shared within the SwiftUI `WindowGroup`; Phase 1A is designed for one browser window. Independent multi-window tab sets are out of scope.
- The shell has no download progress or completed-download list. Private tabs have a transient text label on native surfaces, overview and palette; a webpage in the uncluttered canvas has no permanent private indicator, so use Privacy or the palette to inspect its mode.
- The native new-tab view, introduction, handbook, palette and tab overview have state/routing tests and isolated-bundle UI tests for selected focus, menu access, shortcuts, onboarding Skip, the full three-step flow, and handbook Replay. VoiceOver behavior still needs hands-on checking. Light and Debug-forced dark captures were inspected for Phase 1A; the Phase 1B overview capture was inspected in dark appearance. Light-appearance overview inspection remains pending.
- A normal Debug build signs successfully with App Sandbox, network-client, and user-selected read/write entitlements. A release distribution build and notarization are not yet verified.
- Title-bar color matching uses computed solid root/body CSS backgrounds. Gradient or image-backed top surfaces, transparent pages, CSS color formats outside standard computed rgb/rgba, and script-driven theme changes while a tab remains active may use the semantic system window color or the last detected color. Color is refreshed after navigation, once shortly afterward, and when a tab is activated; it is not sampled from pixels or persisted across relaunch. Automated light/dark New Tab and light Settings screenshots were inspected. Live-site matching, window dragging, traffic-light interaction, and fullscreen entry/exit still need hands-on checks.
- Paper now advertises a Safari-compatible desktop WebKit identity, with an honest Paper token. WebKit still lacks Chromium `navigator.userAgentData` and Chromium client hints; sites may choose different features. If the installed Safari version or WebKit UA cannot be read, Paper uses WebKit's app-token identity. The identity of an already-open session is not changed in place by an app update.
- The signed-out Google Search comparison showed the desktop categories and AI Mode label with the new identity, but Safari's signed-out layout, all signed-in states, account eligibility, regional experiments, and knowledge-panel variations remain unverified. A headless Chrome request got an unusual-traffic challenge. Reddit also displayed a JavaScript challenge in the isolated cross-site smoke test. YouTube playback, authenticated Gmail/Docs, uploads, and site-specific popups need manual checks. See [web-compatibility.md](web-compatibility.md).
- Phase 2A compiles conservative subsets of EasyList and EasyPrivacy. Unsupported exceptions, scriptlets, procedural cosmetics, redirect/removal modifiers, and rules beyond explicit caps are not applied. See [filter-list-compatibility.md](filter-list-compatibility.md) for exact coverage. First-run navigation before asynchronous compilation finishes can load unblocked resources; later rule updates do not reload pages automatically.
- WebKit exposes no supported per-request `WKContentRuleList` match callback to this app, so per-tab blocked-request and tracker totals are unavailable. Cosmetic counts represent distinct initial selector matches, not all elements ever hidden. YouTube video ads may remain. Per-site bypass changes can require a reload to clear already loaded content or injected CSS.
- Signed Debug fixture tests cover native rule compilation, cache reuse, fallback, local third-party blocking, and cosmetic hiding. A single 1/5/10/20-tab offscreen local-fixture timing run is recorded in [content-blocker.md](content-blocker.md); app-process memory samples were too noisy to quantify blocker overhead and excluded WebContent processes. A signed-out WebKit visual smoke loaded six sites, but a sponsored Reddit post remained visible, consent overlays limited inspection on The Guardian and The Verge, and YouTube playback was not tested. Login/media breakage, interactive site checks, blocker-off comparisons, and repeatable memory/page-load measurements remain before Phase 2A is declared complete. The macOS XCTest UI runner timed out enabling automation on both the live-site attempt and an existing short test.

- The bundled Public Suffix List is a dated offline snapshot. Newly delegated suffixes may temporarily map by its implicit wildcard rule. There is no periodic PSL update yet.
- Site data records identify types and display names, not values. Current-site clearing only removes records whose display names map to the same registrable domain, plus matching cookies. Ambiguous WebKit records may remain. Clearing a registrable site includes its subdomains.
- The popup adapter can open a requested URL in another Paper tab, but it returns no new `WKWebView` to the requesting page. Opener-dependent OAuth flows and blank popups may fail. Google sign-in and OAuth need physical app testing without real credentials in automation.
- Notifications have no editable Paper decision because the installed public WebKit macOS delegate lacks that hook. Media and geolocation permission prompts still depend on macOS TCC and actual device/site testing.
- VoiceOver traversal of the new Privacy sheet, permission alerts, and Settings controls needs hands-on verification. Automated focus and accessibility labels do not establish physical VoiceOver behavior.
