# Known limitations

- Accounts V1 infers sessions from conservative secure/HttpOnly cookie-name patterns; it cannot prove server-side login state, show identities, distinguish multiple accounts on one provider, or detect every authentication mechanism. Its provider catalog can age. Sign Out clears local session-bearing storage for selected registrable domains, not server sessions or federated domains; WebKit data records with ambiguous names may remain. Synthetic cookie and UI tests passed, but real Google/GitHub/Reddit login/logout, cross-domain sign-in, and VoiceOver behavior require hands-on checks. See [accounts.md](accounts.md).

- Voice Commands V1 has transcript-driven unit tests and a signed build, but its microphone permission flow, Apple on-device recognition, physical push-to-talk timing, VoiceOver announcement behavior, and quiet/noisy-room accuracy require hands-on validation. On-device recognition may be unavailable for the current locale; there is no network fallback. Voice idle CPU, memory, and end-to-end latency are not yet measured. See [voice-commands.md](voice-commands.md).

- Phase 2E's visual script acts only on a small fixed set of high-confidence, main-frame DOM patterns. Existing cosmetic CSS may hide an ad before this layer can replace it; cross-origin frames and unrecognized sponsored cards remain untouched. One signed-out Guardian viewport showed seven replacements, while Reddit's sampled feed showed none. The six-site smoke did not scroll or validate sticky ads, full-site false positives, idle CPU, WebContent memory, or VoiceOver. See [visual-blocking.md](visual-blocking.md).
- Popup suppression allows native direct links, blocks ordinary scripted requests, and asks for recognized sign-in/payment destinations. WebKit's native action does not provide a universal user-activation bit, so clicked script-driven popups to unrecognized URLs may be blocked. Blank windows and `window.opener` dependent OAuth remain unsupported; no credentialed OAuth/payment flow was tested. See [popup-policy.md](popup-policy.md).
- The 10 October Phase 2E core test run passed with `ContentBlockerBenchmarkTests` excluded. That existing benchmark's hard-coded `/private/tmp/paper-phase2d2-engine-partitions.json` write failed under the signed XCTest app sandbox (`NSCocoaErrorDomain 513`); it was not a visual-blocker assertion failure. The focused visual/popup fixtures and signed-out live smoke passed.

- Phase 2D.2 adds validated advanced static CSS and portable prepared rule artifacts; it does not implement procedural text matching, page-world scriptlets, or YouTube player/ad manipulation. The main-frame-only style sheet is capped at 500 selectors/32 KiB; unsupported selectors and cross-origin subframe content remain uncovered. See [Stage 2](blocker-v2-stage2.md).
- Phase 2D.2 local core/WebKit tests passed before the final partition default was restored to 1,000. The integrated 500/1,000 partition comparison also passed and favored 1,000. A final signed build, final full core rerun, fresh UI suite, and fresh live-site smoke could not run because Xcode was absent from `/Applications` and `xcodebuild` resolved only to Command Line Tools on 9 October. The pre-existing 4/13 isolated UI suite result remains unresolved and cannot be classified reliably without its runner diagnostics. No new live-site cosmetic improvement or YouTube playback claim is made for this phase. Recorded benchmark samples remain available in [blocker-performance.md](blocker-performance.md).

- Blocker V2 Stage 1 raises the operational cap to 10,000 network rules per approved source and expands a WebKit-native syntax subset. It remains partial EasyList/EasyPrivacy compatibility. Cross-source network exceptions, partial resource exceptions, mixed include/exclude domain filters, broad procedures/scriptlets, response rewriting, and reliable YouTube video-ad removal are unsupported. Cosmetic CSS is host-selected at navigation and limited to 500 selectors/32 KiB; short-lived cross-host redirects or script-only route changes may need a reload for newly relevant CSS. See [stage 1](blocker-v2-stage1.md).
- The Stage 1 signed-out live smoke captured ten public pages and one normally playing, seekable YouTube video, but did not validate real sign-ins, purchases, long media sessions, fullscreen playback, or physical app interaction. YouTube home and Twitch still had loading placeholders in their short snapshots. See [performance and smoke results](performance-benchmarks.md).
- The Stage 1 isolated-bundle UI XCTest rerun passed 4 of 13 cases. The other 9 cases had keyboard focus, overlay discovery, or window screenshot assertions fail while the runner repeatedly reported display lookup errors. This suite remains unresolved; focused blocker/WebKit fixtures and the signed live smoke do not replace it.
- The 9 October [uBlock audit](ublock-feasibility.md) led to Stage 1's independent declarative implementation. Safari uBO Lite's extension APIs are still unavailable inside Paper's WKWebView. Later [Blocker V2](blocker-v2-architecture.md) runtime stages have no implementation or performance measurements.

- URL restoration reopens tabs and preserves their order and active index. It does not restore form state, per-tab back/forward history, scroll position, or in-memory JavaScript state after app relaunch.
- Isolated-bundle XCTest UI scenarios now verify several native keyboard paths and new-tab focus. Webpage keyboard/mouse interaction and trackpad scrolling still need hands-on verification.
- WebKit history swipes are enabled by default, and the preference now updates open sessions. Option-swipe tab switching remains opt-in and needs physical trackpad verification. App-local swipe events cannot prove behavior over every nested scroller, webpage drag target, Mission Control configuration, or fullscreen desktop gesture; use Control-Tab and Control-Shift-Tab if it conflicts.
- Tab overview previews are static and may be stale until navigation completes or their five-minute freshness limit expires; viewport-only and script-only page changes do not invalidate them immediately. A never-visible, loading, failed, or unsnapshotable page shows a placeholder. Preview capture is bounded; it is not a live miniature web view.
- `⌘⇧\` and overview search/dismissal passed synthetic UI automation. Physical keyboard and VoiceOver focus order still need hands-on checks.
- Save Panel downloads are implemented but an end-to-end saved-file check remains. File-overwrite behavior and server-provided filenames need manual confirmation.
- Popup requests with a URL open in a new tab. A script-created blank popup with no URL is not represented yet.
- Browser state is shared within the SwiftUI `WindowGroup`; Phase 1A is designed for one browser window. Independent multi-window tab sets are out of scope.
- The shell has no download progress or completed-download list. Private tabs have a transient text label on native surfaces, overview and palette; a webpage in the uncluttered canvas has no permanent private indicator, so use Privacy or the palette to inspect its mode.
- The native new-tab view, introduction, handbook, palette and tab overview have state/routing tests and isolated-bundle UI tests for selected focus, menu access, shortcuts, onboarding Skip, the full three-step flow, and handbook Replay. VoiceOver behavior still needs hands-on checking. Light and Debug-forced dark captures were inspected for Phase 1A; the Phase 1B overview capture was inspected in dark appearance. Light-appearance overview inspection remains pending.
- A normal Debug build signs successfully with App Sandbox, network-client, and user-selected read/write entitlements. A release distribution build and notarization are not yet verified.
- Title-bar color matching uses computed solid root/body CSS backgrounds. Gradient or image-backed top surfaces, transparent pages, CSS color formats outside standard computed rgb/rgba, and script-driven theme changes while a tab remains active may use the semantic system window color or the last detected color. Color is refreshed after navigation, once shortly afterward, and when a tab is activated; it is not sampled from pixels or persisted across relaunch. Automated light/dark New Tab and light Settings screenshots were inspected. Live-site matching, window dragging, traffic-light interaction, and fullscreen entry/exit still need hands-on checks.
- Paper now advertises a Safari-compatible desktop WebKit identity, with an honest Paper token. WebKit still lacks Chromium `navigator.userAgentData` and Chromium client hints; sites may choose different features. If the installed Safari version or WebKit UA cannot be read, Paper uses WebKit's app-token identity. The identity of an already-open session is not changed in place by an app update.
- The signed-out Google Search comparison showed the desktop categories and AI Mode label with the new identity, but Safari's signed-out layout, all signed-in states, account eligibility, regional experiments, and knowledge-panel variations remain unverified. A headless Chrome request got an unusual-traffic challenge. Reddit also displayed a JavaScript challenge in the isolated cross-site smoke test. YouTube playback, authenticated Gmail/Docs, uploads, and site-specific popups need manual checks. See [web-compatibility.md](web-compatibility.md).
- Paper compiles conservative subsets of EasyList and EasyPrivacy. Stage 1 supports only narrow exact network and cosmetic exceptions; broader exceptions, scriptlets, procedural cosmetics beyond validated CSS, redirect/removal modifiers, and rules beyond explicit caps are not applied. See [filter-list-compatibility.md](filter-list-compatibility.md) for exact coverage. First-run navigation before asynchronous compilation finishes can load unblocked resources; later rule updates do not reload pages automatically.
- WebKit exposes no supported per-request `WKContentRuleList` match callback to this app, so per-tab blocked-request and tracker totals are unavailable. Cosmetic counts represent distinct initial selector matches, not all elements ever hidden. YouTube video ads may remain. Per-site bypass changes can require a reload to clear already loaded content or injected CSS.
- Signed Debug fixture tests cover native rule compilation, cache reuse, fallback, local third-party blocking, and cosmetic hiding. A single 1/5/10/20-tab offscreen local-fixture timing run is recorded in [content-blocker.md](content-blocker.md); app-process memory samples were too noisy to quantify blocker overhead and excluded WebContent processes. A signed-out WebKit visual smoke loaded six sites, but a sponsored Reddit post remained visible, consent overlays limited inspection on The Guardian and The Verge, and YouTube playback was not tested. Login/media breakage, interactive site checks, blocker-off comparisons, and repeatable memory/page-load measurements remain before Phase 2A is declared complete. The macOS XCTest UI runner timed out enabling automation on both the live-site attempt and an existing short test.

- The bundled Public Suffix List is a dated offline snapshot. Newly delegated suffixes may temporarily map by its implicit wildcard rule. There is no periodic PSL update yet.
- Site data records identify types and display names, not values. Current-site clearing only removes records whose display names map to the same registrable domain, plus matching cookies. Ambiguous WebKit records may remain. Clearing a registrable site includes its subdomains.
- The popup adapter can open an allowed request URL in another Paper tab, but it returns no new `WKWebView` to the requesting page. Opener-dependent OAuth flows and blank popups may fail. Google sign-in and OAuth need physical app testing without real credentials in automation.
- Notifications have no editable Paper decision because the installed public WebKit macOS delegate lacks that hook. Media and geolocation permission prompts still depend on macOS TCC and actual device/site testing.
- VoiceOver traversal of the new Privacy sheet, permission alerts, and Settings controls needs hands-on verification. Automated focus and accessibility labels do not establish physical VoiceOver behavior.
- Phase 2C signed-out live WebKit testing reproduced YouTube pre-roll ads. A test-only fetch-response change did not stop them; a test-only initial-response change suppressed one observed ad but delayed ordinary playback by roughly 26 seconds. No YouTube-specific runtime blocker ships. Mid-roll, Shorts, signed-in, and broader playback modes remain unverified; see [youtube-blocking.md](youtube-blocking.md).
